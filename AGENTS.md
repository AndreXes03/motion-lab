# Motion Lab: visual delivery protocol

A passing build, metadata check or deterministic seek is technical evidence, not evidence of visual quality.

Before delivering a changed product film:
1. Inspect the supplied reference and state concrete shape, material and lighting targets. Never silently substitute plush for inflatable vinyl or an arbitrary font for a logo.
2. Render isolated clean and clay views with `node scripts/quality.mjs`. Review silhouette, thickness, normals, surface intersections, pivots, decals and texture scale. Fix visible failures before rendering the full film.
3. For mechanical assemblies, confirm the rotation axis and hierarchy; chains must remain attached through motion. Distinguish constrained approximation from a full rigid-body simulation.
4. Render the contact sheet and a video preview. Inspect intermediate fast-travel frames as well as hero frames. Compositing must have an off switch and must not hide defective geometry.
5. Export and verify duration, frame count, dimensions, fps, and seek determinism. Preserve prior versions and report remaining visual limitations without claiming reference equivalence.

Stable configuration: project/look.json, project/motion.json, src/config.js.
Inspection parameters: {"inspect":{"object":"device.root","yaw":20},"review":"clean"}. Modes: beauty, clean, clay, normals.
Do not alter shared files while another agent is rendering a quality gate; coordinate component ownership and announce when a file is stable.

For product-film modeling, impact animation, lens choreography and final delivery, use the repository skill at `.agents/skills/motion-lab-product-film/SKILL.md`. It documents the working renderer and efficient checks without replacing the user's current creative or publication instructions.

For new 3D product scenes, start with `src/scenes/product-starter.js` and import reusable parts through `src/product-kit/index.js`. See `docs/PRODUCT_KIT.md` for model/material ownership, controls and render commands. Preserve existing authored films when improving shared tools.

For an optional photorealism still, use `scripts/photoreal.mjs` and `docs/PHOTOREALISM.md`. Install experiment dependencies separately. This path does not replace the film renderer; report its material adaptations and inspect the exported image before publication.

## Required agent selected controls for every scene

Every new or revised scene must ship with real editable controls and an agent-authored tool layout. Treat control selection as part of creating the video: choose the tools that help adjust its actual motion, lens, lights, materials and compositing. Keep the normal workspace focused and put secondary controls in advanced panels. Do not expose every catalog entry indiscriminately or invent unsupported sliders just to increase the count.

Use this workflow:

1. Inspect the scene's implemented parameters with `node scripts/controls.mjs catalog --scene ID`. Add missing public capabilities before exposing them. Existing study adapters use `parameters.sceneControls`; definitions live in `src/engine/scene-capabilities.js`, and the shared catalog is `src/engine/control-catalog.js`. Preserve each authored default and absolute-time seeking.
2. Choose a small useful selection, panel titles, category order and advanced flags. Categories are Motion, Lens, Lights, Compositing, Character, Graphics and Appearance. Reuse shared widgets and panel templates; build a custom widget only when an existing tool cannot represent the parameter accurately.
3. Preview a validated configuration with `node scripts/controls.mjs plan --scene ID --controls IDs --advanced compositing --reason "Why these tools suit the video"`. For custom panels, pass a version 1 manifest through `--file`. Save it with `node scripts/controls.mjs set`; this updates only that scene in `project/control-selections.json`. Give the selection a concise rationale. Do not leave the scene without an authored selection, even if the full catalog exists. Follow the coverage contract in docs/ADAPTIVE_CONTROLS.md: expose meaningful motion, lens, lights, appearance and finishing in both Easy and Pro; report selected/available counts and justify omissions. Planning ranges are not quotas.
4. Register supported camera/object groups and authored shot windows in `src/engine/animation-groups.js`. Sample only that target’s pose clock; film time, visibility, cuts, captions and unrelated groups must stay unchanged. Prefer a first-shot camera clip and an identity linear curve as the starting point. New curves use group-local rates or per-parameter `animation.rates`; legacy `animation.rate` is migration input only.
5. Curate scene lighting, compositing and interpolation profiles in `project/control-presets.json`. Keep three useful variants where appropriate, at most four per scene/category and at most 15 native control values in a lighting/compositing profile. Give each profile a visible purpose. Inspect with `preset-catalog`, validate with `node scripts/controls.mjs preset-plan --scene ID --category lights|compositing|interpolation --file profile.json`, then save through `preset-set`. Replace an existing ID when the category already has four profiles. Interpolation may inherit the shared palette or use a scene override; preserve other scenes.
6. Verify that the selected controls actually affect representative frames, numeric tools and supported groups can be keyframed, defaults preserve the approved film, and reset/random seeking remain deterministic. Confirm recipe import/export and server validation agree. The UI manifest controls visibility; hiding a tool must retain its existing animation tracks.
7. Run `node scripts/controls.mjs check`, `node scripts/test-scene-control-contract.mjs`, `node scripts/test-motion-workflow.mjs`, the focused scene/browser checks and the build. The build runs these contracts plus the browser-free render-policy and Cycles contract checks automatically. The contract must cover every registered scene and fail when a future scene lacks capabilities or its chosen panel layout. Technical checks do not substitute for the visual delivery protocol above.

Desktop is the reference for the complete tool workspace. Mobile may provide simpler essential controls. Do not require runtime AI inference for this authoring workflow: the coding agent selects and saves the tool layout while making the video. In-app model integration is a separate capability.

Preview quality is a browser-local interaction preference. Auto, Balanced, Fast and Sharp must not change saved parameters, final dimensions, temporal samples or final renderer choice. Compare full-effect frames when judging lighting, materials and compositing; fast previews may bypass expensive effects. See `docs/ADAPTIVE_CONTROLS.md` for schemas and agent CLI examples, and `docs/RENDERER_SELECTION.md` for the separate renderer strategy, local PULSE Cycles capability and prepared mixed-render requirements. Keep renderer-policy and backend ownership coordinated.

For every new or revised video, choose an agent-authored final-render intent and recommendation within implemented adapter support, and save the scene-specific decision in `project/render-plans.json`. Existing scenes without an explicit recommendation retain the safe Three.js default until revised. Preserve it in `parameters.renderPolicy`. Base the choice on implemented adapter support and measured local capability: the current Cycles adapter supports PULSE only. Unsupported explicit engines must be blocked; Auto may explain a safe fallback. Mixed requires rendered inputs and a prepared local compositing plan. Keep preview quality independent, and verify representative converted frames before claiming picture fidelity.

- Register meaningful animation groups and shot windows. Existing native keyframes must remain visible in the curve editor. For camera motion defined by functions, expose actual evaluated pose channels through the scene's `animationState`/`animationChannels` or `captureAuthoredAnimation` adapter. Label sampled observations honestly; do not invent keyframes or apply existing easing a second time. Inspecting or opening the editor must preserve the default frame and saved parameters.

Perspective lens controls must always be paired with real camera distance and subject-size compensation in the same visible Lens panel. Reuse `src/engine/camera-lens.js` after resetting each authored camera pose and before depth-of-field calculation or rendering. Defaults must preserve existing films. Add the pair to new 3D scenes and verify preview, saved recipes, parameter animation and final-render camera parity. Pure 2D scenes must not expose a fictitious perspective lens.
